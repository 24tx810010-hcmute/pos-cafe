## Concrete harness weaknesses, without causal overclaim

1. **The route completion barrier is incomplete.** At `idempotencyRecovery.spec.ts:89`, `committed=true` precedes `await route.abort('failed')`. The body at line91 polls only `committed`, then advances global `private.write_clock()` by three days. This permits the clock change while ACK abortion and old-page recovery reads remain in flight. Database commit has been observed, but network loss has not been awaited to completion. This possibility is proved by controlled Promise scheduling in `control-flow-oracles.json`; it is not proof that this ordering caused the historical fresh-browser timeout.

2. **Manual finally can discard the first useful error.** The fresh context's entire login/list/detail/assertion sequence and close share line92. A rejection from `fresh.close()` in `finally` replaces a body error in JavaScript. Independent actual Chromium/Playwright oracles below demonstrate the lost original locator error and show fixture-owned teardown preserves it. The historical evidence does not establish whether close was a secondary failure or itself the original stalled operation, so it must not be labeled solely a harmless teardown failure.

3. **Post-timeout clock restoration can contaminate a diagnostic snapshot.** `TimeoutManager.withRunnable` in installed `node_modules/playwright/lib/worker/workerProcessEntry.js:1797–1832` uses `Promise.race([cb(), timeoutPromise])`. Losing that race does not cancel the test callback. After the timeout, runner cleanup proceeds; this spec's `test.afterEach(()=>h.clock(null))` at line4 restores real wall-clock before normal context fixture teardown (worker code around3056–3069). Sessions issued at the test's 11 September clock can then fail the 12-hour check at `014_write_identity_and_ledger.sql:191` under real 14 September time. The original page's session can also expire at the earlier three-day jump. Thus the session-expired text in the snapshot may be a consequence of these clock transitions, rather than the trigger for the timeout.

4. **The snapshot is not page-identified.** Installed Playwright `lib/index.js:623–640` records `context.pages()[0]` for the first available `_pageSnapshot` at context close; its later fallback around660 also takes a remaining context. The artifact carries no context ID. Therefore the old report's inference that the snapshot was definitely the original page was stronger than the evidence warrants. It is compatible with the original page, and potentially a fresh page after clock restoration; the exact provenance cannot be recovered from this artifact.

5. **The diagnostic boundary is too broad.** `idempotencyHarness.ts:11` combines navigation and pairing clicks; line16 employee readiness and line25 operation-row clicking have default action waits bounded chiefly by the global test budget. The whole fresh flow occupies one source line. `pairAndUnlock` attaches its response listener before `page.goto`, but only enters `try/finally` at the passcode wait on line12, so earlier navigation/click errors bypass that listener cleanup. These affect failure localization and cleanup reliability, not an established business regression.

## Proposed deterministic follow-up for the parent

Keep the 45-second test limit and retries0. Use named, bounded phases for real setup, pairing, observed terminal commit + ACK drop, fresh pairing, fresh list, fresh detail, and final database assertion. The helper's cleanup should encompass its whole listener lifetime. Record phase/context labels, sanitized RPC method/path/status/error-code and durations; do not record PIN/store key/token/header/body credentials.

Replace the manual fresh-context finally with a fixture-owned fresh-page factory: creation remains at the intended point in the test, while fixture teardown owns closure after the body. Preserve the first body failure and surface any teardown failure separately, as the real Playwright oracle demonstrates. Do not suppress all cleanup failures. Ensure old and fresh contexts are closed before the global clock is restored, with explicit ownership so a timeout cannot leave requests changing the diagnostic state during cleanup.

Await both the route's abort completion and the matching browser `requestfailed` observation after a known database commit. Register the browser listener before clicking, and match the intended RPC/key in memory without printing credentials. Close the original page after this barrier and before advancing the clock; this reflects the intended lost-local/new-device scenario and prevents its polling from mixing with fresh-browser recovery. Keep the final server-side terminal state/payment-count oracle intact.

For deterministic sensitivity, hold a fresh-browser list/detail response and release it only after the named phase deadline. The test must fail with that phase and request/page identity before the global timeout. Separately inject a cleanup error: the named body failure must remain the first error and cleanup must remain observable. A successful body with injected cleanup failure must still fail. Run these as controlled harness checks, separately from accepted business executions.

Then run the unchanged business assertions repeatedly and sequentially on the same preflight-approved isolated backend, preserving every failed run and exact candidate metadata. A new pass series can demonstrate current stability over those runs and that evidence is now diagnostic; without reproducing the original blocked operation, the honest conclusion remains **harness races/error masking hardened; historical timeout trigger not conclusively identified**.

## Conclusion

No new application fault is proved by these artifacts. Two concrete harness issues are established: the partial ACK-drop barrier and loss of a body error through manual finally. Fixture-owned teardown has independent actual Playwright support. The original 45-second trigger remains unknown, and the previous assumption about which page supplied the error snapshot should be treated as unproven. No deployment verification was performed by this reviewer.
